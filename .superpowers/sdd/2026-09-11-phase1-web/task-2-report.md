## Defect found in the brief's literal test code (reported per instructions)

The brief's `types.generated.test.ts` computes the schema/committed-file paths as:

```ts
const here = new URL('.', import.meta.url).pathname
```

On Windows this yields `/C:/Users/.../web/src/api/` (leading slash before the drive
letter). Passing that into `node:path`'s `join()` on win32 produces a **doubled
drive letter** — `join('/C:/Users/.../src/api/', 'schema.json')` →
`\C:\Users\...\src\api\schema.json` — which `fs.readFileSync` cannot open
(`ENOENT: ... 'C:\C:\Users\...\schema.json'`). I reproduced this in plain Node
(no Vitest/jsdom involved), so it is not the jsdom/`import.meta.url` issue the
brief anticipated with the `environmentMatchGlobs` mechanism — it persisted even
after routing the test through the `node` environment.

Fix applied (minimal, preserves everything else in the file verbatim):

```ts
import { dirname, join } from 'node:path'
import { fileURLToPath } from 'node:url'
...
const here = dirname(fileURLToPath(import.meta.url))
```

This is the standard portable way to get a directory path from `import.meta.url`
and resolves correctly on Windows (verified in isolation before touching the test
file — see TDD evidence below, second RED run).

I did not touch the test's assertions, the generator invocation, the flags, or the
type-name list — only the two-line path-resolution helper needed to make the test
runnable on this Windows dev machine at all.

### Finding 1 (Important) — DEP0190 warning not pristine

The brief's `execFileSync('npx', [...], { shell: process.platform === 'win32' })`
triggers Node's `DEP0190` deprecation on every Windows run (argv array + `shell:
true`). Fixed by invoking `json-schema-to-typescript`'s own CLI entrypoint
directly via `process.execPath`, dropping the shell entirely, while keeping the
exact same generator flags:

```ts
const require = createRequire(import.meta.url)
const json2tsPackageJson = require.resolve('json-schema-to-typescript/package.json')
const json2tsBin = (require(json2tsPackageJson) as { bin: { json2ts: string } }).bin.json2ts
const json2tsCli = join(dirname(json2tsPackageJson), json2tsBin)
...
execFileSync(
  process.execPath,
  [json2tsCli, '--input', schema, '--output', out,
   '--style.singleQuote', '--no-additionalProperties', '--unreachableDefinitions'],
  { stdio: 'pipe' },
)
```

**How the entrypoint is resolved, and why it's stable:** `json-schema-to-typescript`'s
`package.json` has no `"exports"` map (confirmed by reading it directly), so
`require.resolve('json-schema-to-typescript/package.json')` resolves via plain
CommonJS resolution — nothing blocks the subpath. From that resolved path I read
the package's own `"bin": { "json2ts": "dist/src/cli.js" }` field at runtime and
join it against the package's directory, rather than hard-coding `dist/src/cli.js`
inline. If the package ever moves its CLI file, this still finds it, because it's
reading the same manifest field `npm`/`npx` themselves use to know what `json2ts`
points to. I did not switch to the JS API (`compileFromFile`) per the explicit
ruling — this still runs the actual CLI module as a child process, so flag
parsing and output (banner comment, formatting) are identical to what `gen:types`
produces; the only change is *how* the CLI process is launched (no shell), not
*which* code path builds the output.

Verified byte-for-byte before wiring it into the test:
```
node -e "... execFileSync(process.execPath, [cliEntry, ...]); compare to committed file ..."
→ identical: true
```

## Fix round 2 (newline-independence)

New finding from the controller's own investigation after reading the round-1
report: the guard's byte comparison only passes today because both sides happen
to be CRLF on this machine (`core.autocrlf=true`, no `.gitattributes`, and the
committed blob for `types.generated.ts` itself contains CRLF). On Linux/macOS/CI
a fresh `json2ts` run emits LF while the checked-out committed file still carries
CRLF, so the guard would fail for a platform reason unrelated to real drift.

### Fix applied

Normalise `\r\n` to `\n` on both sides before comparing, and add an assertion
message pointing at the fix when it genuinely fails:

```ts
const normalizeNewlines = (text: string): string => text.replace(/\r\n/g, '\n')
...
const committedContent = normalizeNewlines(readFileSync(committed, 'utf8'))
const freshContent = normalizeNewlines(readFileSync(out, 'utf8'))
expect(
  committedContent,
  'web/src/api/types.generated.ts is stale relative to web/src/api/schema.json — run `npm run gen:types` and commit the result',
).toBe(freshContent)
```

Nothing else changed: no `.gitattributes` added (repo-wide normalisation is
Task 21's), `types.generated.ts` was not re-committed with different line
endings, and the comparison still requires exact content equality — only line
endings are folded.
